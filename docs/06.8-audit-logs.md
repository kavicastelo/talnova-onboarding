# Talnova Onboarding

# 06.8 — Audit Logs Collection

**Collection Name**

```text
auditLogs
```

---

# Purpose

The Audit Logs collection provides a complete, immutable record of all important actions performed within the platform.

This collection exists for:

* Security monitoring
* Compliance requirements
* Internal investigations
* Change tracking
* Administrative accountability
* Employee activity monitoring
* Data integrity verification

Unlike notifications, audit logs are never modified after creation.

They act as the system's source of truth for historical events.

---

# Design Principles

Audit logs must be:

* Immutable
* Append-only
* Searchable
* Tenant isolated
* Long-term retained
* Exportable
* Compliance-friendly

No audit log should ever be deleted manually.

Only retention policies may archive logs.

---

# What Gets Logged

The platform should automatically create audit events for:

### Authentication

* Login success
* Login failure
* Logout
* Password reset
* Invitation acceptance
* MFA events (future)

### User Management

* Employee created
* Employee updated
* Employee deactivated
* Employee deleted
* Role changed
* Department changed
* Team changed

### Journey Management

* Journey created
* Journey updated
* Journey archived
* Journey deleted
* Step created
* Step modified

### Assignment Events

* Assignment created
* Assignment completed
* Assignment cancelled
* Assignment reassigned
* Due date changed

### Content Events

* Knowledge article created
* Knowledge article updated
* Knowledge article deleted
* Upload created
* Upload removed

### Organization Events

* Branding changed
* Security settings changed
* Department created
* Team created
* Location updated

### Security Events

* Unauthorized access attempts
* Permission violations
* Suspicious activity
* API abuse detection

# Severity Levels

## Info

Normal system actions.

Examples:

* Login
* Logout
* Assignment completion
* Content updates

```ts
{
  severity: "info"
}
```

---

## Warning

Potential issues.

Examples:

* Multiple failed logins
* Assignment reassignment
* Permission changes

```ts
{
  severity: "warning"
}
```

---

## Critical

Security-sensitive events.

Examples:

* Unauthorized access
* Security setting changes
* Role escalation
* Suspicious API activity

```ts
{
  severity: "critical"
}
```

---

# Change Tracking

When updates occur, store previous and new values.

Example:

```ts
{
  metadata: {

    previousValue: {
      title: "Old Title"
    },

    newValue: {
      title: "New Title"
    }

  }
}
```

This enables complete historical reconstruction.

```ts
  createdAt: -1
```
```ts
})
```

---

```ts

  resourceType: "journey",

})
```

---

Security events:

```ts

  severity: "critical"

```

---

Date range filtering:

```ts
db.auditLogs.find({
  createdAt: {
    $gte: startDate,
    $lte: endDate
```

* Archival queries

No update methods should exist.
